# DashPal BLE protocol v2 (app copy)

The authoritative copy is the firmware's `docs/BLE_PROTOCOL.md` (repo `deployment-stack`). This file repeats it for readers of the app. The frame codec is `protocol.ts`, the handshakes and sealed frames `auth.ts` (over `crypto.ts`), the pairing code and its link `label.ts`; the golden vectors are `__fixtures__/ble_vectors.json`, byte-identical to the firmware's `tests/ble_vectors.json` (its `v2` section: the code, INFO, the handshakes, sealed frames).

**Alerts in one paragraph (firmware doc §1).** The dashcam sends every alert, tier 1 to 3, to its connected primary phone, and the phone acknowledges each one; the buzzer is the fallback, never a second speaker. While a phone is connected (authenticated and synced) the dashcam routes each new alert to it and keeps its buzzer silent while it waits for the phone's answer and while the phone plays it. The ALERT itself wakes a suspended iOS app; the Android app keeps a foreground service (the DashPal link service) while a DashPal is paired. "Connected" never means "the phone can play sound": the phone must answer each routed alert within `device.ble_ack_ms` (default 750 ms; a critical alert within `min(ble_ack_ms, 400 ms)`) or the buzzer plays it, a phone whose fresh STATE says it cannot play gets nothing routed, and a confirmed alert whose phone sends nothing for more than 3 s (1.5 s for a critical) goes to the buzzer. The buzzer plays an alert only when no phone is connected, the phone cannot play it, does not answer in time, goes quiet or disconnects, or the driver turned on "Also beep on DashPal". The no-face alert sounds only through a live phone (the primary link, its last STATE within its TTL).

**Security in one paragraph (firmware doc §1, §2).** Every frame is 20 bytes or less and travels sealed: once a phone has authenticated, every frame in both directions is encrypted and authenticated with AES-128-GCM under keys new for that connection and carries a counter, so it can be neither read, changed nor replayed (a sealed frame is at most 40 bytes; sessions need an ATT MTU of 43 or more). Only a phone that knows the DashPal's pairing code can pair, and every connection proves both sides: each DashPal has a random 128-bit pairing code in its eFuse, printed as a QR code under its mount and on its box card; pairing proves the code on both sides, bound to a fresh nonce of the dashcam's, and agrees a per-phone key by X25519; every connection proves that key on both sides with fresh nonces, and a phone may run that proof again on a connection that is already up. There is no Bluetooth bonding. Pairing happens only in the pairing window, one phone per window, and every pairing plays the paired chime.

Codec rules both sides share (firmware doc §3): a receiver checks, in this order, length < 2 (`short`), a type that is not of this direction (`type`), a version other than 1 (`version`), a length below the type's v1 length (`short`); it accepts longer frames and ignores trailing and reserved bytes; a sender never sends more than 20 bytes. The frame version byte stays 1; the link version (INFO `proto`) is 2.

## Protocol

### 1 GATT and advertising
Base UUID `d5a1xxxx-7b3e-4c8a-9f21-0c6e5a7d2b10`.

| Item | xxxx | Properties | Access |
|---|---|---|---|
| DashPal service | `0001` | advertised while the pairing window is closed | — |
| Pairing service (empty) | `00f0` | advertised instead of `0001` while the window is open | — |
| `INFO` | `0002` | read | open |
| `IDENTIFY` | `0003` | write with response | always refused with ATT `0x80` (kept so the attribute handles stay stable); an authenticated phone makes the dashcam beep with COMMAND 1 |
| `TX` | `0004` | notify + read | notify (a read returns the empty value); frames go only to an authenticated link, sealed (§1.3) |
| `RX` | `0005` | write + write-without-response | dropped unless the link is authenticated; a frame that does not open is dropped and counted, and 32 in one session end the link |
| `AUTH` | `0006` | write with response + read | open; the pairing and session handshakes (§1.2). The last characteristic, so no other handle moved |

Plus the Device Information Service `0x180A` (manufacturer "DashPal", model "DP-1", firmware revision "dms-core x.y"), not advertised. The attribute table never changes shape between the two advertising states.

**INFO payload** (read, 30 bytes): `[ver u8 = 1][proto_min u8 = 2][proto_max u8 = 2][fw_major u8][fw_minor u8][mac 6 bytes, identity address, MSB first][peer_bonded u8, always 0][bond_count u8, phones paired 0-4][flags u8: bit0 pairing_open, bit1 setup_busy (another link holds the setup claim), bit2 keyed (the board has a pairing code)][Nc 16 bytes]`. `Nc` is 16 random bytes for the reader's connection: drawn at connect, redrawn every time a PAIR_REQ on that connection reaches its code check (pass or fail), wiped on disconnect; public (it makes a captured PAIR_REQ useless anywhere else and blinds the phone's session id). A reader accepts 14 bytes or more with `ver = 1` and reads `Nc` only from 30 bytes or more; the phone reads INFO again before every SESSION_REQ. `dashcam_id` (phone side) = lowercase hex of `mac` (12 chars). The name suffix `XXXX` = the last 2 bytes of that same MAC, uppercase hex.

Advertising: ADV = flags + one 128-bit UUID (`0001` or `00f0`); scan response = complete local name `DashPal-XXXX`. Public identity address, no peripheral privacy. Intervals: 20 ms for 30 s after boot, after a disconnect and while the pairing window is open; then 152.5 ms; 1022.5 ms while one phone is connected; stop at 2 links. Default TX power. The phone's setup scans in low-latency mode on Android (ble-manager's default is low power).

Security (firmware doc §2):

- No Bluetooth pairing or bonding: the NimBLE security manager is off and the link layer is not encrypted. All security is in the AUTH handshakes (§1.2) and the sealed frames (§1.3).
- **Pairing code:** 16 random bytes `S` in eFuse `BLOCK_USR_DATA` bytes 4-19 (bytes 0-3 `DPK1`, 20-23 the CRC-32 of bytes 0-19, little-endian), written once on the board by `ble keygen confirm` from its hardware random number generator, then write-protected. A DashPal without a valid block is unkeyed (INFO bit 2 = 0) and refuses pairing (`R_UNKEYED`). The code text is the Crockford base32 (`0123456789ABCDEFGHJKMNPQRSTVWXYZ`) of `S` and a check byte `SHA-256("DashPal code v1" || S)[0]`: 136 bits as 28 characters, the last 4 padding bits zero, shown in 7 groups of 4. Typed input is case-insensitive, ignores spaces and `-`, reads `I` and `L` as `1` and `O` as `0`, and refuses `U`. The label link is `https://<LINK_DOMAIN>/dashpal#d=<dashcam_id>&k=<code, 28 characters>` (the parameters in the fragment never reach a web server; the app's `extra.linkDomain` and the firmware's `CONFIG_DMS_LINK_DOMAIN` are the same domain); the app also reads `roadwise://dashpal` and never shows one with a code. `ble label` prints the code only while no phone is paired, and the app never shows it.
- **One-time code:** an authenticated phone's ADD_PHONE opens the window and arms a 16-byte code `S1` for it; a PAIR_REQ may prove `S1` instead of `S`. Its check byte is `SHA-256("DashPal once v1" || S1)[0]`, and the phone draws `S1` again until its two check bytes differ (and it is not all zero), so a code text is exactly one kind (the label kind wins a tie). `S1` lives in RAM and is wiped when the window ends; the phone shows it as a QR code of its link and never stores it.
- **AUTH answers:** every well-formed AUTH write is answered with ATT 0, and its verdict is the AUTH read value (a RESULT record `[0xE0][2][code]`, or PAIR_RESP / SESSION_RESP). A malformed write is answered ATT `0x80` and changes nothing. The dashcam never answers 5, 15 or 0x89 on any characteristic. The phone treats any non-zero status of an AUTH write (and a write that never settles) as a transport fault, never a verdict.
- **Authenticated** = the connection completed SESSION_FIN. Only authenticated connections get frames, may be primary, and may send commands. The phone names itself in SESSION_REQ by `bid`, an HMAC under its key over the connection's `Nc`, so its id never travels in clear after the PAIR_REQ that created it.
- **Setup claim:** taken by a PAIR_REQ whose code tag checks, while the window is open and no other connection holds it. It ends when its connection drops, when its pairing is stored, 15 s after the PAIR_REQ that took it (later requests never extend it), or when the window is opened or explicitly closed (a window timeout does not end it).
- A new pairing is stored only from the claimant's valid PAIR_FIN, and the first one closes the window. Up to 4 phones are kept. A new one replaces `prev_id` only when `prev_proof` proves that record's key; otherwise it is a new phone and replaces the oldest whose phone is not authenticated now. No new pairing may use a stored id.
- A connection that is not authenticated is disconnected: 1 s after a failed code tag or proof on it; the claim holder when its claim ends; otherwise 30 s after connecting if it connected while the window was open (as long as it stays open); otherwise 5 s after connecting, or 10 s once a SESSION_REQ was accepted on it, and 10 s after a stored pairing. A failure never affects another connection.
- A PAIR_REQ on an authenticated connection is allowed; a valid one drops that connection's session first, and a failed one only counts toward the connection's 32.
- Every stored pairing plays `SOUND_PAIRED` + LED pattern from the firmware itself.
- After the first authentication the firmware asks for interval 15–30 ms, latency 0, supervision 6 s; MTU 247 (Android asks for it).
- Not covered: someone who has read the pairing code and is in range during an open window can pair (the chime, the phone count and the phone's new-phone notice expose it; 10 presses remove every phone); a phone that paired from the label can pair again in a later window; physical access with a computer (reflashing, a flash dump); a device that holds a code it made itself cannot be told from a genuine DashPal; no forward secrecy between sessions of one pairing; denial of service, including ending a live connection by over-the-air injection.
- **Pairing window**: no phone paired → open for the first 10 minutes after each boot; otherwise 120 s after 5 presses of the BOOT button, 10 presses (every phone forgotten first), the `ble pair` console command, COMMAND 3 or ADD_PHONE ("Add another phone"). Opening it (again) ends any setup claim and wipes any one-time code (ADD_PHONE then arms its own). It closes when the time is up or at the first stored pairing. While open, the pairing service UUID is advertised.

### 1.2 AUTH handshakes (firmware doc §2.2)
All integers little-endian; labels ASCII without a terminator; `mac` = INFO's 6 bytes, MSB first. Primitives: X25519 (RFC 7748; an all-zero shared secret refused), SHA-256, HMAC-SHA-256, HKDF-SHA-256 (RFC 5869), AES-128-GCM (12-byte nonce, 16-byte tag); every tag and proof compared in constant time; proofs and tags are HMAC-SHA-256 truncated to 16 bytes.

AUTH read value (the record of the connection's last well-formed write): `0x00` pending (1 byte) | PAIR_RESP `[0x90][2][B 32][Nd 16][proof_d 16]` (66) | SESSION_RESP `[0xA0][2][Nd 16][proof_d 16]` (34) | RESULT `[0xE0][2][code]` (3). Result codes: `0x00` R_OK, `0x01` R_NOT_NOW, `0x02` R_UNKNOWN_PHONE, `0x03` R_BUSY, `0x04` R_WRONG_PROOF, `0x05` R_WRONG_CODE, `0x06` R_UNKEYED, `0x07` R_ID_IN_USE, `0x08` R_STORE_FAILED, `0x09` R_MTU.

**Pairing.** PAIR_REQ (98 bytes) `[0x10][2][id_p 8][prev_id 8][prev_proof 16][A 32][Np 16][tag 16]`, `tag = HMAC(code, "DPv2 pair-req" || mac || Nc || id_p || prev_id || prev_proof || A || Np)[0..16]`, `prev_proof = HMAC(K_pair of prev_id, "DPv2 replace" || mac || Nc || id_p)[0..16]` (all zero for no `prev_id`), `code` = `S` or the armed `S1`, `Nc` = the connection's current one. Checked in order: (1) length 98, type, version, else ATT `0x80`; (2) keyed, else R_UNKEYED; (3) MTU ≥ 43, else R_MTU; (4) not condemned and not computing, else R_NOT_NOW; (5) the window open or this connection holds the live claim, else R_NOT_NOW; (6) no other connection holds a live claim, else R_BUSY; (7) `id_p` not zero and not stored, else R_ID_IN_USE (`Nc` kept: a new `id_p` at once); (8) the tag under `S1` or `S`, `Nc` redrawn now pass or fail, else R_WRONG_CODE (a connection not authenticated condemned, ended 1 s later). Then `Z = X25519(b, A)`, `T_pair = SHA-256("DPv2 pair" || mac || Nc || id_p || prev_id || prev_proof || A || Np || B || Nd)`, `OKM = HKDF(salt = code, IKM = Z, info = T_pair, 64)`: `K_pair = OKM[0..32]`, `k_conf = OKM[32..64]`, `proof_d = HMAC(k_conf, "DPv2 dashcam" || T_pair)[0..16]`, `proof_p = HMAC(k_conf, "DPv2 phone" || T_pair)[0..16]` (`Nc` here is the one the tag was checked against). The phone checks `proof_d` (wrong: it disconnects and stores nothing), keeps the key as pending, then PAIR_FIN `[0x11][2][proof_p 16]` and reads the RESULT: R_NOT_NOW (nothing pending, the claim gone, condemned), R_WRONG_PROOF (condemned, nothing stored), R_STORE_FAILED (nothing stored, no chime), R_OK (stored and persisted, the claim used up, the chime, the window closed, the one-time code wiped). When the dashcam cannot compute its answer itself, the RESULT is R_NOT_NOW, the claim kept to its end: the phone reads INFO again and, when it is keyed and not busy and the window is open or the phone holds the claim, sends a new PAIR_REQ after 300 ms (a new key pair and `Np`, the same `id_p`, the new `Nc`), at most twice per setup connection. After R_OK the phone reads INFO again (a new `Nc`) and runs the session on the same connection.

**Session** (every connection, and again on one already up). SESSION_REQ (26) `[0x20][2][bid 8][Np 16]`, `bid = HMAC(K_pair, "DPv2 id" || mac || Nc)[0..8]`: MTU < 43 → R_MTU; a pairing computing or awaiting its FIN, or condemned → R_NOT_NOW; no record's `bid` matches → R_UNKNOWN_PHONE; an authenticated connection and another phone's record → R_NOT_NOW; otherwise SESSION_RESP. `T_s = SHA-256("DPv2 session" || mac || id_p || Np || Nd)`, `OKM = HKDF(salt = Np || Nd, IKM = K_pair, info = T_s, 48)`: `k_dp = OKM[0..16]` (dashcam → phone), `k_pd = OKM[16..32]` (phone → dashcam), `k_conf = OKM[32..48]`, the proofs as above over `T_s`. SESSION_FIN (18) `[0x21][2][proof_p 16]`, then the RESULT: R_NOT_NOW (nothing pending, condemned); R_WRONG_PROOF (a connection not authenticated condemned; a re-handshake keeps its current keys and counts toward 32); R_OK (the first session: the keys installed, counters 0, the same phone on the other connection disconnected; a re-handshake: the new keys replace the old and the connection is not synced until its next COMMAND 7, so an alert routed to it goes to the buzzer). The dashcam switches keys when the FIN verifies; the phone tries the new receive key first and the old one for frames sealed before the switch, and seals with the new key only after reading R_OK. An iOS state-restoration relaunch with the connection kept runs the session again on it.

### 1.3 Sealed frames (firmware doc §3.3)
Envelope (TX notify and RX write): `[ctr u32 LE][AES-128-GCM ciphertext of the frame][tag 16]`; the inner frame is an unchanged frame of §2 (2-20 bytes, byte 1 = 1). Dashcam → phone: key `k_dp`, `dir = 0x01`; phone → dashcam: key `k_pd`, `dir = 0x02`; nonce `[dir][0 x 7][ctr u32 LE]`; aad `[0x02][dir]`; `ctr` 0 at each session start per direction, +1 for every seal (a notify NimBLE refused or a write that failed included), never reused; at 2^32 − 1 the sender ends the connection. The dashcam seals just before NimBLE takes the notification; the phone seals inside the queued GATT operation as it runs, so an ALERT_ACK that jumps the queue still takes the next counter. Opening: fewer than 22 bytes or a tag that does not verify → dropped and counted (32 such frames, failed re-handshake FINs or failed PAIR_REQ tags in one session end the connection: the dashcam terminates it, the phone disconnects and reconnects); then the replay window, after the tag: accepted if `ctr` is above the highest seen, or up to 63 below it and not seen; otherwise dropped and counted, the connection kept. The phone drops TX notifications that arrive before its session, uncounted. The app writes RX with `maxByteSize` 64 and AUTH with 128, so ble-manager never splits a write.

### 2 Framing
Little-endian. Byte 0 = type, byte 1 = protocol version `1` (the frame version stays 1; every frame travels sealed, §1.3). A receiver **accepts a frame whose length is ≥ the v1 length for its type and ignores trailing bytes**; shorter frames, unknown types and other versions are dropped and counted (never crash). Max 20 bytes.

**Dashcam → phone (TX notify)**

| Type | Name | Fields after `[type][ver]` | Len |
|---|---|---|---|
| `0x01` | HELLO | `boot_id u32, next_seq u32, oldest_seq u32, uptime_ms u32` | 18 |
| `0x02` | STATUS | `uptime_ms u32, state u8, flags u8, fps_x10 u8, temp_c i8, bond_count u8` | 11 |
| `0x03` | EVENT | `seq u32, t_ms u32, dur_ds u16, ev u8, tier_aud u8, detail u8, value_x10 i16, rsv u8` | 18 |
| `0x04` | ALERT | `alert_id u16, sound u8, tier u8, level u8, mode u8, route u8, rsv u8, uptime_ms u32` | 14 |
| `0x05` | ALERT_STOP | `alert_id u16, reason u8` | 5 |
| `0x06` | ALERT_FALLBACK | `alert_id u16, cause u8` | 5 |
| `0x07` | TIME_ECHO | `req_id u16, uptime_ms u32` | 8 |
| `0x08` | PAIRED | `bond_count u8` | 3 |

- `boot_id`: a **random non-zero u32 drawn every boot** (`bootloader_random_enable()` + `esp_fill_random`, or after the RF is up). Never a counter (NVS is erased by merged-image flashes). The phone only compares for equality.
- `seq`: per-boot event counter from 0. `next_seq` = the seq the next new event gets. `oldest_seq` = the oldest seq still in the replay ring.
- `t_ms` = dashcam uptime (ms) when the rule fired; `dur_ds` = `(t − t_start)` in 0.1 s (saturating at 65535); condition start = `t_ms − dur_ds·100`. u32 uptime wraps after 49.7 days: the phone treats a decrease of `uptime_ms` within one boot as a new offset epoch (documented, not otherwise handled).
- `ev` = engine event id in the frozen `dms/alerts.py` `EventType` order: 0 MICROSLEEP, 1 SLEEP, 2 UNRESPONSIVE, 3 LONG_GLANCE, 4 VATS, 5 FACE_LOST, 6 FATIGUE_DROWSY, 7 FATIGUE_SEVERE, 8 FATIGUE_EARLY, 9 PHONE_PATTERN, 10 REPEATED_DISTRACTION, 11 MONITORING_LIMITED, 12 GLANCE, 13 LOOK_BACK, 14 YAWN, 15 HEAD_NOD, 16 REPEAT_MICROSLEEP, 17 GAZE_CONCENTRATION, 18 NO_SCANNING, 19 FATIGUE_LEVEL, 20 CALIBRATED, 21 CALIBRATION_LOW_CONFIDENCE, 22 CALIBRATION_RESET, 23 CAMERA_BUMP, 24 DRIVER_CHANGE, 25 RECENTRED, 26 POSTURE_CHANGE, 27 ZONE_LEARNED, 28 NUISANCE_TAG, 29 MONITORING_RESTORED, 30 PHONE_HANDHELD, 31 CRITICAL_STAND_DOWN (tier 0, log only: a critical alert stopped because the face had been gone 30 s with no known speed ≥ 10 km/h; `value` = seconds gone). Append-only. Unknown ids are stored as `UNKNOWN_<n>` and never scored.
- `tier_aud`: bits 0–1 tier, bit 7 `audible` (engine "would sound"; independent of mute/shadow/route).
- `detail`: 0 none; UNRESPONSIVE: 1 `no_return` (D4, after a distraction warning), 2 `eyes_closed`, 3 `no_return_critical` (F3, after a critical); MICROSLEEP: 4 `nod`; CRITICAL_STAND_DOWN: 5 `face_gone`. Any other detail is sent as 0.
- `value_x10` = engine `value` × 10, clamped to i16.
- STATUS `state`: 0 booting, 1 no_face, 2 calibrating, 3 monitoring, 4 limited, 5 paused (overheat / preview / bench / HIL / camcheck / replay), 6 camera_error (runtime camera failure). `flags`: bit0 muted (mute or shadow), bit1 pairing_open, bit2 time_synced, bit3 calibrated (detection ready), bit4 primary (this link is the dashcam's primary link, §3.4), bit5 buzzer_active, bit6 live (a blink was detected in the last 60 s). Sent after HELLO, on any state/flags change, **every 500 ms to a link any alert is routed to** (a continuous alert, or a one-shot waiting for its ALERT_ACK or confirmed; a confirmed one-shot for 3 s after its confirm), whatever the age of its STATE, and periodically: every 2 s (1 s while an alert is active) to links whose last STATE arrived < 10 s ago; other links get STATUS on change only. The 500-ms STATUS wakes a suspended iOS app and ticks an Android app whose JS timers are paused, so the phone's repeats, its playback-failure timers and its STATEs keep going while it plays the alert.
- ALERT `sound` (computed from the `alert_sounds` state, identical in typed and tiers mode): 1 glance (warning from LONG_GLANCE / VATS, SOUND_DISTRACTION or SOUND_WARNING), 2 drowsy (SOUND_DROWSY or the fatigue override), 3 wake (SOUND_CRITICAL / SOUND_DROWSY_CRITICAL), 4 phone (UNSAFE(_ONCE) or a chime caused by PHONE_PATTERN / PHONE_HANDHELD), 5 chime (any other audible advisory one-shot), 6 no_face (the no-face alert: the driver's face out of view while the phone reports the car moving; FACE_LOST; buzzer SOUND_NO_FACE, two beeps every 5 s; continuous, tier 2, silent on both outputs while no phone is live). A phone treats a `sound` it does not know as the chime (level 1, every 2.5 s): an app that predates sound 6 plays the no-face alert as a continuous chime and, because it is continuous, holds other audio ducked and mutes its own event tones for as long as the face is out of view. The app and the firmware ship together; there is no capability negotiation. **Never routed, gated or sent as ALERT**: READY, SYSTEM, BOOT, TAG_ACK, TEST, TEST_TYPES, IDENTIFY, PAIRED and COMMAND-6 test sounds. `tier` 1–3; `level` 0–3 (critical escalation step, else 0); `mode` 0 once, 1 continuous; `route` 1 = routed to this phone (ACK required within the firmware's `device.ble_ack_ms`, default 750), 0 = informational (visual + haptic only, never ACK, never play sound). `alert_id` per boot, wraps, never 0.
- **Alert identity**: a change of `tier` or `sound` ends the alert (ALERT_STOP reason 1) and starts a new `alert_id`; a `level` change re-sends ALERT with the same id and needs no new ACK.
- ALERT_STOP `reason`: 0 cleared (including paused / sleep / overheat), 1 superseded, 2 muted. ALERT_FALLBACK `cause`: 1 no ACK in time, 2 phone said cannot (at any time, also after a confirm), 3 the phone was lost (another link became primary, the phone disconnected, its fresh STATE dropped `can_play`, a confirmed continuous alert's phone sent nothing for more than 3 s, 1.5 s for a critical, or the phone sent COMMAND 7 hello again: its app started over and forgot the alert), 4 reserved: the dashcam does not send it; a phone that receives it keeps playing.

**Phone → dashcam (RX write)**

| Type | Name | Fields after `[type][ver]` | Len |
|---|---|---|---|
| `0x81` | STATE | `flags u8, ttl_ds u8, speed_cms u16, local_min u16, boot_id u32, ack_seq u32` | 16 |
| `0x82` | ACK | `boot_id u32, ack_seq u32` | 10 |
| `0x83` | ALERT_ACK | `alert_id u16, outcome u8` | 5 |
| `0x84` | TIME_PING | `req_id u16, epoch_ms u64` | 12 |
| `0x85` | RESUME | `boot_id u32, next_seq u32` | 10 |
| `0x86` | COMMAND | `op u8, arg u8` | 4 |

- ADD_PHONE `0x88`, 18 bytes, `[0x88][1][code 16]`: accepted only sealed from an authenticated phone (the table codec does not list it; the dashcam handles it before the codec); opens the pairing window for 120 s and arms this one-time code for it (an all-zero or short code is ignored and the window still opens); the code is wiped when the window ends.

- STATE (the phone's context and its "cannot play" signal): `flags` bit0 `can_play`, bit1 `buzzer_too`, bit2 `drive_active`, bit3 `speed_valid`; `ttl_ds` how long the STATE counts as fresh, in 0.1 s (phone sends 30; dashcam clamps 10..50); a fresh STATE without `can_play` stops routing to that phone, a stale or missing one does not; `speed_cms` cm/s (meaningful only with `speed_valid`); `local_min` 0–1439 or `0xFFFF`; `boot_id` + `ack_seq`: cumulative ack for that boot (all `seq < ack_seq` persisted; `0` = nothing yet). The dashcam ignores an ack whose `boot_id` is not its current one. The dashcam uses acks for diagnostics only (`ble` status "unacked"); replay happens only on RESUME.
- ALERT_ACK `outcome`: 1 playing, 0 cannot. The phone answers every `route=1` ALERT immediately with 1 or 0, and sends 0 later if playback fails or is interrupted. A new `route=1` ALERT that arrives before the phone has a clock offset for the dashcam's boot on this connection gets ALERT_ACK(0) and is shown without sound. The phone judges an ALERT late (more than 750 ms after `uptime_ms`, 400 ms for tier 3, the dashcam's default deadlines) only with an offset measured on this connection in the last 10 minutes; without one it does not judge it, sends TIME_PINGs at once, and the dashcam's deadline and ALERT_FALLBACK decide.
- TIME_PING: phone epoch ms at send; the dashcam answers TIME_ECHO and stores `epoch_offset = epoch_ms − uptime_ms` (good to ± one-way latency) for its own logs (`events.jsonl` `unix`, `trip.json`).
- RESUME: the phone's per-boot cursor. Dashcam: if `boot_id` = current boot and `next_seq ≤ dashcam next_seq` → send HELLO + STATUS, then every ring event with `seq ≥ next_seq`; otherwise → HELLO + STATUS, then the whole ring from `oldest_seq`.
- COMMAND `op`: 1 identify (identify melody + LED ~3 s; an authenticated phone's "beep my DashPal"), 2 recalibrate, 3 open the pairing window (authenticated phones only; 120 s, until one new phone pairs; ends any setup claim), 4 forget me (deletes this phone's pairing record, persisted, then disconnects), 5 pair confirm (phone UX; plays nothing extra if a pairing chime already played in the last 10 s, else the paired chime; sends PAIRED), 6 test sound (`arg` = sound 1–5 on the buzzer), **7 hello** (dashcam answers HELLO + STATUS and, if an alert is active, ALERT with `route=0`; a hello on a link that already has alerts routed to it means the phone's app started over and forgot them: the continuous alert, confirmed or not, and every one-shot still waiting for its ALERT_ACK fall back to the buzzer, cause 3, before the STATUS; a one-shot already confirmed stays as it is).

### 3 Connection sequence (phone)
1. Connect: iOS pending connect by peripheral identifier; Android `connect(id,{autoconnect:true})` re-issued after **every** disconnect (ble-manager closes the GATT on disconnect), or a direct connect after a foreground scan.
2. Android `requestMTU(247)`; both `retrieveServices` (no `AUTH`: Android refreshes its cache once; still missing, the attempt fails).
3. **Read INFO** (`Nc`); SESSION_REQ, SESSION_RESP, SESSION_FIN, RESULT (§1.2), within 5 s. On R_UNKNOWN_PHONE, or INFO `proto` below 2, the phone shows it needs setting up again but keeps retrying (30 s, then every 60 s); on a wrong dashcam proof or another `mac` it disconnects and sends nothing. A non-zero ATT status on an AUTH write is a transport fault, never a verdict.
4. `startNotification(TX)`, then sealed **COMMAND 7 hello**.
5. On HELLO: TIME_PING ×3 (100 ms apart); **RESUME after the 3 echoes or 500 ms**, whichever first; then STATE at least every second while the app is in the foreground, a drive is open, or the phone is sounding a DashPal alert (every 450 ms while it sounds a critical one); otherwise only when its flags change (and the first one after RESUME). With the app in the Android background JS timers are paused, so during a drive STATE goes out once per drive row instead: a row sends it unless one went out in the last 300 ms (the row's timer pump or a dashcam frame just sent it). Rows come once a second, location or not, and a row closes up to 1.5 s after its second, so rows come up to about 2.5 s apart and STATEs at most about 2.8 s apart, inside the 3 s TTL. With no drive open, the dashcam's frames (STATUS every 500 ms to the phone playing its alert) tick the link instead.
6. TIME_PING ×3 again every 10 min (triggered from the link tick).

Setup (a new phone, while the window is open; no system pairing dialog; `setup.ts`): read INFO (keyed, window open, not busy, `Nc`); PAIR_REQ; read AUTH until it is not pending (every 100 ms, up to 3 s); check the proof; PAIR_FIN; read the RESULT; read INFO again (new `Nc`); the session on the same connection; COMMAND 7, COMMAND 5, PAIRED. Busy (flags bit 1 or R_BUSY): read INFO again every second for up to 16 s. R_NOT_NOW to a PAIR_REQ (its first verdict, or in place of the pending answer): read INFO again; when it is keyed and not busy, and the window is open or the phone holds the claim (a request of its own was answered pending or PAIR_RESP less than 15 s ago), wait 300 ms and send a new PAIR_REQ (a new key pair and `Np`, the same `id_p`, the new `Nc`). At most 2 such retries per setup connection; after them, or when INFO does not allow one, the window closed means the phone asks for the button, anything else is a failed setup. A retry never extends the claim. Add another phone: the paired phone sends ADD_PHONE with a fresh one-time code and shows it as a QR code; the new phone pairs under it.

### 4 Routing (dashcam, `ble_link`)
- **Primary link** (at most one) among authenticated, synced links, by the first rule that has a candidate: (1) links whose STATE is under 10 s old and has `drive_active`; (2) links whose STATE is under 10 s old and has `can_play`; in both the current primary if it qualifies, else the one whose STATE arrived last; (3) the current primary, for as long as it stays connected, authenticated and synced; (4) the link heard from last (any valid RX frame). STATUS bit4 tells each link whether it is primary. A primary change while an alert is routed hands that alert to the buzzer (cause 3).
- **Routing target** = the primary, unless its last STATE is within its TTL and lacks `can_play`. A primary with no STATE yet, or an older one, is the target: the ALERT wakes it and its ALERT_ACK decides.
- **Live phone** = the primary with its last STATE within its TTL, whether or not it can play (the no-face alert and the engine's `phone_live` input).
- **Continuous sound starts** (an episode runs from `cont ≠ NONE` to `cont = NONE`):
  - every tier, 1 to 3, with a routing target and the episode not yet fallen back: ALERT `route=1` to the target, the continuous gate closes (buzzer silent, a critical included; its rhythm keeps running underneath), deadline = time the ALERT was handed to NimBLE successfully + `ble_ack_ms` (`min(ble_ack_ms, 400)` for tier 3); not handed over within that time of the alert's start counts as a missed deadline too. ACK(1) → confirmed: the buzzer stays silent for as long as the phone plays it and never joins. ACK(0) at any time, a missed deadline, the routing target changing (another primary, a disconnect, a fresh STATE without `can_play`), a hello from the routed link, or a confirmed continuous alert other than sound 6 whose link has sent no valid frame for more than 3 s (1.5 s for tier 3; the quiet guard) → **fallback** (gate opens; the players kept ticking so the rhythm continues in phase); ALERT_FALLBACK to every synced link. Once an episode has fallen back, every later alert in that episode stays on the buzzer (sent with `route=0`).
  - While the continuous sound is critical, no one-shot sounds on the buzzer, gated or not.
  - `buzzer_too` (the routed link's last STATE, whatever its age) → buzzer always plays as well, warnings, critical alerts and one-shots alike (ALERT still `route=1`): the only case where both sound.
  - no routing target → buzzer at once; ALERT `route=0` to every synced link.
- **The no-face alert (sound 6) is phone-only.** The dashcam raises it only while the phone reports the car moving (STATE `speed_valid` at 10 km/h or more for 3 s with three different readings, or for 6 s, until below 10 km/h for 3 s or no speed for 3 s). It is routed as above while a phone is **live**: the primary link, its last STATE within its TTL (`ttl_ds`), whether or not it can play. A fallback while the phone is live (ALERT_ACK(0), a missed deadline, a fresh STATE without `can_play`) hands it to the buzzer as usual; the quiet guard does not apply to it. When no phone is live (a disconnect, or the primary's STATE older than its TTL) the dashcam ends it with ALERT_STOP(0) to every remaining synced link and holds the buzzer silent: no ALERT_FALLBACK, in the same call for a disconnect, within one tick for a lapsed TTL. A sound-6 episode that starts with no live phone sends no ALERT and stays silent. When a phone is live again while the engine still requests it, a new alert starts with normal routing.
- **One-shots** (advisory chimes): with a routing target, the one-shot is **not enqueued in alerts.c**; `ble_link` holds it and, on ACK(0) / deadline / the routing target changing / disconnect before the confirm, calls `alerts_play_once(sound)` at that moment; after a confirm ALERT_ACK(0) is still honoured for 3 s. alerts.c allows a one-shot while a *gated* warning is active, never while the continuous sound is critical. Without a routing target → `alerts_play_once` at once.
- Sound clears → ALERT_STOP(0). Entering a paused state, overheat, preview, deep sleep, HIL reset → every path that stops sound goes through one wrapper `app_sound_set(...)` that informs `ble_link` (ALERT_STOP 0). `mute` → ALERT_STOP(2) and no further ALERT while muted; `unmute` while a sound is active = a new alert start (normal routing).
- On a (re)connect while an alert is active: after HELLO/STATUS send ALERT with `route=0` (visual only; never re-routed).
- ALERT_ACKs are accepted only from the link the alert was routed to.

### 5 Alert handling (phone)
- `route=1` → ALERT_ACK(1) **before** starting playback if the phone can play now, else ALERT_ACK(0); then play (or haptic + visual only). `route=0` → haptic + visual only, no ACK, no sound. Android holds a 5 s wake lock first thing on every `route=1` ALERT and on any frame (at most once a second) while a DashPal alert sounds. A new `route=1` ALERT before the connection has any clock offset (no HELLO yet) → ALERT_ACK(0), haptic + visual only. A new `route=1` ALERT handled more than `LATE_ALERT_MS` (750 ms) after its `uptime_ms`, `LATE_CRITICAL_ALERT_MS` (400 ms) for tier 3 (the dashcam's default deadlines), by the live offset (the best of the samples taken on this connection in the last 10 min, ranked by `rtt / 2 + age × 0.1 ms/s`, so a faster sample that ages out hands over to the best later one; none once the phone's clock has gone back) → ALERT_ACK(0), haptic + visual only; with no live offset the rule is skipped and TIME_PINGs go out at once; a level step of an alert already in the table is never treated as late.
- The phone **can play** when its alert player works, its alert style allows sound, no call is active or ringing, its media volume is at least a quarter of the maximum and no wired or USB headphones (on Android also an LE-audio headset) are connected (other Bluetooth audio and hearing aids count as heard), whether the app is in front, in the background, or woken by the ALERT itself, with or without a drive open (on Android, in the background with no drive recording, only while the DashPal link service runs: the service keeps the app running, so Android lets it take audio focus); after a playback failure it answers ALERT_ACK(0) for 30 s. A critical alert counts as a playback failure when the phone's audio session is not active 500 ms after the alert was asked to play, or its tone has neither loaded nor started 500 ms after that. Can-play is read fresh for each new `route=1` ALERT and from a read at most 500 ms old on each tick.
- Continuous: repeat until ALERT_STOP, ALERT_FALLBACK cause 1–3, disconnect, or **3 s with no frame from the dashcam**. Cause 4 (never sent by the dashcam) → keep playing.
- Repeat cadence (start-to-start, never faster than an item finishes): glance 2.5 s, drowsy 4 s, no face 5 s, wake 1.5 s at level 0 → 1.0 s at level ≥ 2. One-shots once.
- The no-face alert (sound 6) plays the glance tone with the words "Driver not visible", spoken on the first play only and not when another no-face alert ended in the last 60 s. Its plays release the audio session (music comes back between them), and it does not make the phone's own event tones vibration and visual only.
- A new HELLO with a different `boot_id`, or a connect, clears the phone's alert table.

### 6 Events and timeline (phone)
- Per `(dashcam_id, boot_id)` the phone keeps (table `dashcam_boots`): best offset (`epoch − uptime`) with its RTT, and `floor_seq` (= max(floor, HELLO.oldest_seq), raised past the newest pruned event by the prune below; it never falls). Offset starts from HELLO (`receive_time − uptime_ms`, discarded if the HELLO arrived > 1 s after the connect/hello request) and is replaced by any TIME_PING sample with a lower RTT (`(send + recv)/2 − echo.uptime_ms`). The HELLO sample's error can be its whole round trip and a ping's at most half of its own, so the HELLO sample ranks as twice its round trip: a ping over the same link always replaces it, which keeps the error within RTT/2.
- Persist each EVENT with `INSERT OR IGNORE` on `(dashcam_id, boot_id, seq)`, assigning `id` = a fresh lowercase v4 UUID at first insert; an EVENT whose seq is below the boot's stored `floor_seq` is not stored (every seq there is stored, gone from the dashcam, pruned or given up by the prune). Then ACK: cursor = lowest seq ≥ `floor_seq` not yet stored (gaps below `oldest_seq` are permanent and advance the floor). RESUME uses the same cursor.
- An EVENT that arrives while no drive is open (a drive is open from the Start Drive tap until its finalize has finished, the drive-end catch-up included) is persisted and acknowledged like any other, since the cursor needs every seq, but stored with `ignored = 1`, decided as the frame arrives. The first copy's flag stands: a replayed copy is a duplicate and changes nothing. A drive claims only events with `ignored = 0` whose condition start (`offset + t_ms − dur_ds·100`) lies inside it, so an event that started before the drive and arrives during it (a replay after a mid-drive reconnect) stays unclaimed. Unclaimed events, ignored ones included, are deleted 7 days after receipt: the prune first raises each such boot's `floor_seq` past the newest of them, so the cursor never moves back (a link up for over a week on one boot stays synced, and no RESUME asks for a pruned seq) and a re-sent pruned seq, a whole-ring replay included, is not stored again. A gap below a pruned event is given up with it: seqs rise with time on one boot, so whatever fills it started over 7 days ago and no drive could claim it.
- A HELLO whose `boot_id` matches a stored boot but whose `next_seq` is below the stored max seq + 1 → treat as a new boot (should not happen with random ids; defence in depth).
- Wall times are **derived when needed** (facts at finalize, timeline display) from `t_ms`, `dur_ds` and the best offset at that moment; columns `at_ms`/`started_at_ms` are only a cache.

### 7 Context (dashcam)
`ble_link_context(now)`: `speed_kmh` = the last STATE speed if that STATE had `speed_valid` and is ≤ 10 s old; a STATE with `speed_valid = 0` makes it NaN at once. Only the primary link's STATE counts. `local_min` = last received value advanced by elapsed uptime (NaN if never received). `yaw_rate_dps` = NaN always. Fed into `ctx` before `dms_frontend_process`. Phone sets `speed_valid` only while recording and when the latest drive row is ≤ 2 s old, `gnssValid`, `speed ≥ 0`, and `0 ≤ speedAcc ≤ 2 m/s`.
